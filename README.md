# memomy — 創作活動向け作業記録アプリ

<img width="1417" height="945" alt="memoy_screen" src="https://github.com/user-attachments/assets/6a3a7ef6-5a86-42ff-8485-1b07faa683ea" />

創作活動向けの作業ログ・タイマー・作業管理アプリです。

作業時間だけでなく、制作途中の画像やコミット、納期、メモなどを
プロジェクト単位で記録できます。

主に創作活動を想定していますが、イラスト制作・音楽制作・プログラミング・勉強など、
さまざまな作業の記録ツールとして利用できます。

## コンセプト

本アプリは創作活動における「作業の記録・可視化」と「継続」を支援することを目的としたツールです。

タイマーによる作業時間の記録と、プロジェクトごとのログ管理を組み合わせることで、
日々どれくらい作業したのか、どのように制作を進めてきたのかを後から振り返ることができます。

また、使用する機器を限定しないWebアプリケーションとして開発することで、

- デジタル環境ではイラストの保存データを添付
- アナログ環境ではスマートフォンで撮影した写真を添付

のように、制作環境に合わせて利用できるツールを目指しています。

## 開発背景

GitHubを用いた開発を行っている中で、コミット履歴から「いつ、何を作業したのか」を後から振り返ることができる体験に価値を感じていました。

一方で、イラスト制作などの創作活動では、プログラミングのように作業履歴が自然に残る仕組みが少なく、
「どれくらい作業してきたのか」「どのように完成まで進めてきたのか」を振り返ることが難しいと感じていました。

そこで、

- 作業時間を自然に記録できる
- プロジェクト単位で作業履歴を残せる
- 制作途中の画像やメモも一緒に記録できる
- 過去の制作過程を振り返り、次の活動につなげられる

という仕組みを自分で作ることにしました。

また、ラフから完成までの制作過程を時系列で記録することで、
生成AIが普及した現在において、**人がどのように時間をかけて制作したのかというプロセスそのものを残すことにも意味があるのではないか**と考えています。

SNS上では、AI生成画像と手描きのイラストをめぐって、
「これはAI生成なのではないか」といった議論が起こることもあります。

memomyに制作過程を記録しておくことで、

> この作品がどのように作られたのか

を作品そのものだけでなく、その制作履歴からも伝えられるようにしたいと考えています。

将来的には、memomyの記録を見ることで、
「この作品はこうやって作られたんだ」と制作過程まで含めて理解してもらえるような、
創作活動の記録基盤になればいいなと考えています。

### 名前の由来

`memomy` は memory（記録） + my（私） から名付けました。

「私自身の制作活動を記録する」というイメージ。
あとは語感が良かったので `memomy` にしました。

## 設計思想

本アプリでは「作業ログを自然に蓄積する」ことを重視しています。

そのため

- タイマー停止時にコミットを促す
- 作業単位をプロジェクトに紐付ける

など、作業フローを崩さないUX設計を意識しました。

タイマー起動 → 作業 → タイマーストップ（保存）

のように単純な操作でプロジェクトの進行を記録でき、プロジェクトごとに振り替えることが可能です。

コミットごとに画像の添付やコメントを残すことができ、長期的な創作活動の過程そのものを蓄積できる仕組みを目指しています。

**memomyを開いてその日の作業が始まり、memomyを閉じてその日の作業が終わる**といった使用を想定しており、自身でも実践しています（便利です）。

## 使用技術
### フロントエンド
- **TypeScript**
  - 静的型付けにより開発時のバグを抑制し、保守性・拡張性の高い設計・実装を実施。
- **React**
  - タイマー・プロジェクト管理・作業ログなど、機能ごとにコンポーネントを分割し、再利用性・保守性を意識して実装。
- **Next.js**
  - ルーティングやページ構成を整理しやすく、将来的なパフォーマンス最適化も見据えて採用。
- **Tailwind CSS**
  - デザインの再現性とコードの可読性を意識。

### ストレージ・データ管理
- **IndexedDB**
  - 画像データ等の大容量データをクライアント側で永続化するため採用。
  - 環境変数による`Flag`でIdb と REST API を変更、開発環境ではAPIを用いたバックエンド永続化で運用。DEMO環境ではIdbを用いています。
  - **今後の展望**: 将来的な認証・認可機能実装に伴い、ユーザー単位でのクラウドデータ保存（https://memomy.net でのREST API運用)ができる設計を考慮

### バックエンド
- **Ruby on Rails  (https://github.com/kei5o55/memomy-backend)**
  - REST APIとして実装。フロントエンドからの作業ログ・プロジェクト等のデータ管理を担当。
  - ActiveRecordなど、便利なORMやその他機能の豊富さから採用
  - Devise / devise-jwtを用いた認証機能を実装中。

詳細は以下のリポジトリに記載しています。

## 工夫
#### 普段の作業フローを崩さない使用感
設計思想部分にも記載してある通り、**「タイマースタートからストっプ・保存まで」** のフローを自然にこなせるようなUX設計を意識しています
基本的には、

- 作業を始める
- Start
- Stop
- 必要に応じてメモや画像を追加して保存

という流れだけで作業記録を残せるようにしています。

#### CI/CDパイプラインによる開発フローの自動化

GitHub Actionsを利用してCI/CDパイプラインを構築しています。

Pull Requestおよび`main`ブランチへのpushをトリガーとして、

* TypeScriptによる型チェック
* ESLintによるコードチェック
* 本番環境を想定したビルドチェック

を自動で実行しています。

また、`main`ブランチへのpush時には、上記のチェックが成功した場合のみVercelへのデプロイを自動実行する構成としています。

#### 永続化を活用したタイマーセッションのライフサイクル設計
- 背景
  - タイマー駆動時、ユーザがページをリロードしたり、ページを遷移した場合に進行中の作業についての経過時間などが消失し、タイマーが初期（00:00:00)より再開する問題があった。

 - **技術的な工夫**
  - **`WorkSession`（状態管理）** と **`Commit`（実績ログ）** を明確に分離。
  - **`WorkSession`**: IndexedDB 上でタイマーモードや状態フラグをキャッシュとして保持し、リロード時にも「今どのモードで動いていたか」を正確に復元できるように設計。
  - **`Commit`**: 作業完了時に必要な確定データ（所要時間・メモ・画像等）のみを集約して Rails API（DB）へ保存し、一時的な状態データは一括クリーンアップする設計
   
このように、一時的な状態（WorkSession）と確定した実績（Commit）を分離することで、タイマーの状態復元と作業履歴の永続化、余分なレコードの増加を防ぐ設計としています。
